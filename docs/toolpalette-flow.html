構成

システム構成

4つの層に分かれている。ネイティブC++(ToolPalette.gup)が 3ds Max SDKに直接触れる唯一の層で、それを FPStaticInterface 経由でPythonに公開する。Python側はさらに「pymxsに触れない純粋な層」と 「pymxsで橋渡しするだけの薄い層」に分けてある。

起動

起動シーケンス

3ds Max起動〜ツールバー復元〜Pythonブートストラップまでの流れ。 アイコン用Qtリソースの登録を、ツールバー復元(アイコン解決)より確実に早く終わらせることが 最大の設計目的になっている。

既知の罠 — アイコン消失

Qtリソース登録がツールバー復元より1回でも遅れると、解決失敗の結果がQIconの内部キャッシュに残り、以後登録し直しても再評価されない。

対処: 通知(NOTIFY_TOOLBARS_PRE_LOAD)だけに頼らず、LibInitialize()から同期的に直接登録して間に合わせる。

既知の罠 — 起動タイミングの揺らぎ

LibInitializeからGUP::Start()までの間隔が起動ごとに16ms〜26秒と大きく揺れ、通知ベースの登録だけでは再現性がなかった。

対処: 通知ハンドラは残しつつ、確実な同期登録をLibInitialize()側にも重ねて持たせる。

ランタイム

ドラッグ&ドロップで配置

パレット上のボタンをツールバーへドラッグしたときの処理。UI層(PySide6)は 「どこに何を置くか」の判断を一切持たず、座標とボタン定義を渡すだけで、 実際の配置ロジックはすべてネイティブ側に委譲している。

既知の罠 — 全体ハング

初期実装はgrabMouse()のまま自前のゴーストウィンドウを新規生成しており、3ds Max全体がフリーズした(Application Hang)。

対処: Qt標準のQDragに置き換え、プレビュー表示もQt自身に任せた。

既知の罠 — 無関係ボタンの混入

QMimeData.setText()(text/plain)を使うと、3ds Max純正のドロップ処理がそれを検知し、無関係なボタンを勝手に追加してしまった。

対処: 独自MIMEタイプapplication/x-toolpalette-buttonrefのみを使う。

ランタイム

クリックでマクロ実行

ドラッグ閾値(6px)を超えなかった場合だけ通常クリックとして扱われ、配置ではなくマクロ実行に回る。

リファレンス

公開API — ToolPaletteAPI

FPStaticInterfaceとして公開され、Pythonから pymxs.runtime.ToolPaletteAPI.関数名(...)の形で直接呼べる。 MAXScriptファイルを一切介さない。

関数説明
getMaxHwnd()3ds Maxメインウィンドウの HWND を取得する。
findMacro(macroName, category)該当macroScriptを全ActionTableから検索し、見つかれば内部に tblId/cmdId を保持する。
getLastTblId() / getLastCmdId()直前の findMacro が見つけた ActionTable ID / コマンドID を取得する。
getNativeButtonWidth/Height(hwnd)配置先ツールバー上の純正ボタンを実測し、新規ボタンのサイズを合わせる。
computeInsertPos(hwnd, dropX)ドロップX座標から挿入位置(インデックス)を算出する。
placeButton(hwnd, tblId, cmdId, label, tooltip, pos, iconName, wd, ht)MacroButtonData + ToolMacroItem を組み立て、ツールバーへ実際に配置する。
saveConfig()CUIFrameMgr::WriteConfig() でワークスペース設定を保存する。
findToolbarAtPoint(x, y)画面座標からドロップ先のツールバー HWND を特定する。
